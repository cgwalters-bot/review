# The `agent-board/passes/v1` publication

> This text was generated by an LLM ([how cgwalters uses LLMs](https://github.com/cgwalters/cgwalters#llms)). cgwalters has not reviewed it yet.

What agent-board's scheduler pass publishes about its recent passes, for
the Status page's **Scheduler passes** view (review#245). This repository
holds the contract and the consumer (`src/github/passes.ts`,
`src/github/passesview.ts`); `test/fixtures/passes.json` is the reference
publication. **agent-board does not produce it yet**: that is a separate
change to `crates/board-forge/src/pass` and its `docs/pass.md`, which the
consumer is ready for. Until then the view says the publication is absent.

## Where it is

One comment by the bot's own account on the hold snapshot's issue
(`holds.repository`, `holds.issue`), whose first line is
`<!-- agent-board-passes v1 -->`, followed by a ```` ```json ```` fence
holding one object. The app reads it from the same request as the hold
snapshot and takes the newest such comment by the bot; another author's is
ignored. It is a separate comment, not a key of `agent-board/holds/v1`,
because the hold snapshot is written only after stages 3 and 4 succeed:
a failed or cut-short pass must still be recorded.

The producer writes it only with `holds.passes` set (`false` by default;
needs `holds`). Off by default, it stops a newly deployed revision from
adding a write to every pass, and putting pass error text on the issue,
before the operator has reviewed what it publishes. There is no other
control.

## When it is written

An applying pass writes it once, last, whatever happened before: after a
failed or cut-short stage, after a hold snapshot that was not published,
and when the pass ran out of requests or time (it keeps one write in
reserve for this). It reads the previous comment, puts its own record
first, keeps the newest `retention` (10) records younger than seven days,
and edits the comment in place. A write that fails is one `passes error: …`
line and is not retried. A preview writes nothing today; the `preview`
mode and start state exist so that a record of planned starts, should one
be published, can never read as started.

The records come from typed values captured where the pass makes each
decision: the same places that print `start …`, `hold …`, `pools: …`,
`… error: …` and `summary: …` today. The producer must not parse its own
log.

Limits the reader must assume:

- A pass that is killed (job timeout, cancelled, lost runner) writes
  nothing, and nothing later records it. Gaps between records are not
  detected.
- A pass whose write fails loses its record: the next pass carries only
  what the comment held.
- So an old `published_at` means the pass stopped, or stopped publishing.
  The app marks a publication or reading older than an hour as stale, and
  never shows a stale or missing one as healthy.

## The object

Every key is present; `null` where there is no value. Within v1, keys are
only added; readers ignore keys they don't know.

|---|---|---|
| `schema` | `"agent-board/passes/v1"` | |
| `published_at` | RFC 3339 | The writing pass's clock. |
| `retention` | count | How many records the producer keeps (10). |
| `omitted` | count | Whole records left out to fit the byte bound. |
| `passes` | list of pass, at most 10 | Newest first. |
| `pools` | pools or null | The writing pass's pool readings; null where it read none. |
| `in_flight` | in-flight or null | What the writing pass found running or waiting; null where it didn't look. |

| Key | Type | Meaning |
|---|---|---|
| `run` | `{repository, id, attempt}` or null | The pass's own Actions run and attempt; null for `local`. |
| `started_at`, `finished_at` | RFC 3339 | The pass's clock at its start and at the write. |
| `mode` | `actions`, `preview`, `local` | As `holds/v1`'s `pass.mode`. |
| `result` | `success`, `partial`, `failure` | `partial`: a section failed or was cut short and later ones still ran; `failure`: the pass stopped. |
| `sections` | list, at most 16 | `{name, outcome, error}`: `name` a stage token (`setup`, `pull-requests`, `epics`, `schedule`, `maintain`, `status`, `holds`, …), `outcome` `ok`, `failed`, `skipped` or `cut-short`; `error` the failed section's first error line, else null. |

**pools**: `{observed_at, complete, omitted, items}`, at most 16 items
and percentages from 0 to 1000, `complete` false
where some pool was not read; each item `{pool, observed_at, used_percent,
allowed_percent, resets_at, held, ready}`: the reading's own time, percent
of the window used, the percent the pace allows now, when the window
resets, whether the pass holds the pool, and the candidates ready for it;
each null where unknown, never 0 in its place.

**in_flight**: `{observed_at, complete, omitted, runs, prs}`; `runs` (at
most 50) `{item, kind, pool, run, since}` with a required `run`; `prs` (at
most 50) `{repository, number, state, since}`, `state` `merge-queue` or
`review-wait`.

## Bounds and text

Counts are integers from 0 to 1,000,000; ids are positive safe integers.
Repository names are `OWNER/REPO` of `[A-Za-z0-9_.-]`; tokens are
`[a-z][a-z0-9-]{0,31}`. An error is one line of at most 200 characters
with no control characters: the first line of the error, before any
response body. It must not name an inference, broker or tailnet address,
or any URL, IP address or `host:port`; the producer replaces them with
`[address]`, and the app does so again before showing it.

The comment stays under 48 KiB of JSON (the app refuses a body over
60,000 characters). To fit, the producer drops the `starts` and `no_start`
entries of the oldest records first, counting them in each record's
`omitted`, then whole records from the oldest, counting them in the
top-level `omitted`.

## How the app reads it

- No comment: not published (`holds.passes` off, or an older agent-board).
  A comment that can't be used, or a failed read, keeps the last usable
  publication on screen, marked as such; with none, nothing is known.
- A schema other than v1, a malformed header, more than 10 records or an
  oversize body make the whole comment unusable. A malformed record is
  left out and counted; a malformed `pools` or `in_flight` block is unknown
  on its own. An unknown start `state` is read as `uncertain`, never as
  confirmed. `mode`, `result`, section `outcome` and PR `state` are closed
  in v1 (an unknown value makes its record or block unreadable); `reason`,
  `cap`, `hold`, `kind` and section names take newer tokens.
- The issue's comments are read one page of 100 at a time, as for the hold
  snapshot. A full page without the comment is unknown, not absent.
- A time more than an hour old, or more than five minutes ahead of the
  viewer's clock, is stale.
- Links are built from the typed references only: `OWNER/REPO#N` to its
  issue (GitHub redirects a PR), runs to `actions/runs/ID`, PRs to
  `pull/N`. Text is shown as text, never as Markdown or HTML.
- `no-ready-work` is shown as such only where the record's `result` is
  `success`, it lists its sections with none left out, failed or cut
  short, and its candidates were all read with none ready; otherwise it is
  unknown.
- A pool is **well under pace** when `allowed_percent - used_percent` is
  at least 20 points (`UNDER_PACE_POINTS`, fixed in the app so every reader
  agrees). It is flagged only with `ready` 0; the publication, the pools
  block and that pool's reading current; pools complete with none left
  out; no record unreadable or left out; and the newest record's no-ready
  evidence complete as above.
- Where a record's starts were left out, its start count reads "at least".
- An empty list under an incomplete, truncated or stale observation reads
  "unknown", not "none".
